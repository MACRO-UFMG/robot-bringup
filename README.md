# Robot Bringup (ROS 2 Jazzy + Docker Compose)

A modular **ROS 2 Jazzy** bringup system for running robots, sensors, mapping, localization, navigation, and planning inside Docker containers using **Docker Compose profiles**.

This repository is meant to be used as a *stack builder*: you select which components you want, generate a profile list, and start only what you need.

## Overview

This repo contains one Docker Compose service per bringup, grouped by **profiles**. Each bringup is responsible for one subsystem:

- **Robot base / drivers** (e.g., Pioneer, Scout)
- **Sensors** (Livox MID-360, RealSense)
- **Mapping / SLAM** (FAST-LIO2)
- **Localization** (localization stack bringup)
- **Navigation** (Nav2 bringup)
- **Planning** (Polaris planning stack)
- **Utilities** (pointcloud_to_laserscan)
- **Filters** (adaptive_odom_filter)

You can run these components individually or together, depending on your needs.

## Repository Layout

```
robot-bringup/
  config/
    template.env

    robot_bringup/

    scout_bringup/

    adaptive_filter_bringup/
```

> **Important:** relative paths inside Docker Compose are resolved from the directory where the compose file lives (`docker/docker-compose.yml`). If you move files around, adjust paths accordingly.

## Installation

### 1) Clone the repository

```bash
git clone <repository-url>
cd robot-bringup
```

### 2) Initialize submodules (if used)

```bash
git submodule update --init --recursive
```

> Submodules vary by bringup. Check each `src/<bringup>/src/` folder for embedded repos.

### 3) Create your local environment file

This repo expects a local env file at:

- `config/.env`  (not committed; created locally)

Create it from the template:

```bash
cp config/template.env config/.env
```

Then edit `config/.env` to match your network, robot, and sensor setup.

## Configuration

### Environment variables (`config/.env`)

Typical variables you may set (your template may differ):

- ROS networking:
  - `ROS_DOMAIN_ID`
  - `ROS_LOCALHOST_ONLY`
  - `ROS_AUTOMATIC_DISCOVERY_RANGE`
  - `FASTRTPS_DEFAULT_PROFILES_FILE` (if using FastDDS profiles)
- Host/robot IPs:
  - `HOST_IP`, `ROS_IP`, `ROS_HOSTNAME` (only if you use them)
- Sensor IPs:
  - `LIVOX_LIDAR_IP` (if required by your Livox setup)
- Namespaces:
  - `NAMESPACE` (if your stack is namespaced per-robot)

> **Rule of thumb:** keep env vars for **machine-specific** configuration (IP, domain id, namespaces). Keep **algorithm parameters** (filters, SLAM tuning, Nav2 settings) inside YAML parameter files.

## Profiles and Bringups

Below is the current bringup list used by `create_stack.sh` and the expected service roles.

| Bringup Folder | Compose Profile | What it does |
|---|---:|---|
| `robot_bringup` | `ros_base` | Base ROS image and shared runtime dependencies used by other components. |
| `pioneer_bringup` | `pioneer` | Pioneer robot interface / base driver bringup. |
| `scout_bringup` | `scout` | Scout robot interface / base driver bringup. |
| `livox_bringup` | `livox` | Livox LiDAR driver bringup (MID-360). |
| `realsense2_camera_bringup` | `realsense2` | Intel RealSense driver bringup. |

## How to Run

### Quick start (recommended): use the scripts

1) Select what you want to run and generate `config/selected_profiles.conf`:

```bash
./scripts/create_stack.sh
cat config/selected_profiles.conf
```

2) Start the stack based on the selected profiles:

```bash
./scripts/run_robot.sh
```

### Manual start with Docker Compose

You can also run components directly with Docker Compose:

```bash
docker compose -f docker/docker-compose.yml --profile livox up --build
docker compose -f docker/docker-compose.yml --profile realsense2 up --build
docker compose -f docker/docker-compose.yml --profile fastlio2 up --build
docker compose -f docker/docker-compose.yml --profile localization up --build
docker compose -f docker/docker-compose.yml --profile navigation up --build
docker compose -f docker/docker-compose.yml --profile polaris up --build
docker compose -f docker/docker-compose.yml --profile adaptive_filter up --build
```

### Running multiple profiles at once

```bash
docker compose -f docker/docker-compose.yml \
  --profile ros_base \
  --profile scout \
  --profile livox \
  --profile fastlio2 \
  up --build
```

## Parameter Files

Each bringup reads parameters from one or more YAML files. The exact location depends on how the bringup is packaged, but you should look in the following places (in this order):

1) **Bringup-level config folder** (source):
- `src/<bringup_name>/config/`

2) **Upstream package config** (source):
- `src/<bringup_name>/src/<upstream_repo_or_pkg>/config/`

3) **Installed share directory** (inside container after build):
- `/home/<user>/ros2_ws/install/<pkg>/share/<pkg>/config/`
- or `/opt/ros/jazzy/share/<pkg>/...` (for system packages)

### How parameter files are selected

Most bringups follow one of these patterns:

- **Compose environment variable** selects a config:
  - e.g. `CONFIG_FILE=mid360.yaml`, `PARAMS_FILE=nav2.yaml`

- **Launch file argument** selects a config:
  - e.g. `ros2 launch <pkg> <launch>.py params_file:=...`

- **entrypoint.sh default** selects a config if nothing is provided

**When you change parameter files:**
- Prefer **copying** a base config and making a new file (e.g., `mid360_mod.yaml`) rather than editing upstream defaults.
- Keep parameter changes minimal and versioned.
- Use descriptive names: `nav2_coro.yaml`, `mid360_mod.yaml`, `fastlio2_indoor.yaml`, etc.

## Component-by-Component Usage Notes

### 1) `robot_bringup` (`ros_base`)
**Purpose:** shared base runtime used by most stacks (common tools, ROS env, shared dependencies).

**How to run:**
- Usually included automatically by `create_stack.sh`.
- By itself, it may do little besides providing the base image.

**What to watch:**
- Changes here affect many images. Rebuild if you update dependencies.

---

### 2) `pioneer_bringup` (`pioneer`)
**Purpose:** starts the Pioneer robot driver / interface.

**How to run:**
```bash
docker compose -f docker/docker-compose.yml --profile pioneer up --build
```

**Parameters / configs to check:**
- Serial port mapping (commonly `/dev/ttyUSB0`)
- Base frame IDs and TF tree consistency (`base_link`, `odom`, etc.)
- Rate settings (odometry publish frequency)

**Where to look:**
- `src/pioneer_bringup/config/`
- `src/pioneer_bringup/src/.../`

---

### 3) `scout_bringup` (`scout`)
**Purpose:** starts the Scout robot driver / interface.

**How to run:**
```bash
docker compose -f docker/docker-compose.yml --profile scout up --build
```

**Parameters / configs to check:**
- Device mapping under `/dev`
- Base frame IDs (`base_link`, `odom`)
- Command velocity topics (`cmd_vel`) and rate

**Where to look:**
- `src/scout_bringup/config/`
- `src/scout_bringup/src/.../`

---

### 4) `livox_bringup` (`livox`)
**Purpose:** runs Livox MID-360 driver and (optionally) RViz.

**How to run:**
```bash
docker compose -f docker/docker-compose.yml --profile livox up --build
```

**Parameters / configs to check:**
- LiDAR IP / host network settings (`network_mode: host` is typical)
- Publish topic name (point cloud topic)
- Frame ID of LiDAR (`livox_frame` / `mid360` / `lidar_link`, depending on your config)

**Where to look:**
- `src/livox_bringup/config/`
- `src/livox_bringup/src/livox_ros_driver2/...`

---

### 5) `realsense2_camera_bringup` (`realsense2`)
**Purpose:** starts RealSense camera nodes.

**How to run:**
```bash
docker compose -f docker/docker-compose.yml --profile realsense2 up --build
```

**Parameters / configs to check:**
- Enabled streams: color, depth, infrared
- Resolution / FPS
- Frame IDs and TF publishing behavior

**Where to look:**
- `src/realsense2_camera_bringup/config/`
- upstream RealSense ROS params (if vendored)

---

### 6) `fastlio2_bringup` (`fastlio2`)
**Purpose:** mapping / SLAM using FAST-LIO2.

**How to run:**
```bash
docker compose -f docker/docker-compose.yml --profile fastlio2 up --build
```

**Typical config selection:**
- Compose env often sets `CONFIG_FILE` (example: `mid360.yaml`, `mid360_mod.yaml`)

**What to watch when editing FAST-LIO2 params:**
- Topic names: IMU topic and point cloud topic must match your actual drivers.
- Extrinsics: LiDAR↔IMU calibration parameters are critical.
- Frame IDs: map/odom/base frames must be consistent across the stack.
- Rates and time sync: mismatched timestamps will break integration.

**Where to look:**
- `src/fastlio2_bringup/config/`
- `src/fastlio2_bringup/src/FAST_LIO_ROS2/config/`

---

### 7) `pointcloud_to_laserscan_bringup` (`pointcloud_to_laserscan`)
**Purpose:** converts 3D point clouds into 2D LaserScan (useful for 2D obstacle layers, legacy nodes, etc.)

**How to run:**
```bash
docker compose -f docker/docker-compose.yml --profile pointcloud_to_laserscan up --build
```

**What to watch:**
- Input topic must exist (point cloud topic from Livox or from SLAM)
- Output topic must match consumers
- Height filtering, angle limits, range limits

**Where to look:**
- `src/pointcloud_to_laserscan_bringup/config/`
- or upstream package params

---

### 8) `localization_bringup` (`localization`)
**Purpose:** localization stack bringup (often Nav2 localization or AMCL/filters, depending on your implementation).

**How to run:**
```bash
docker compose -f docker/docker-compose.yml --profile localization up --build
```

**What to watch when editing localization params:**
- Which sensor drives localization (laser scan vs point cloud, IMU usage, odom source)
- Frame IDs (`map`, `odom`, `base_link`)
- Map input (if using a static map) and its path/mount
- TF availability: localization will fail silently if TF is incomplete

**Where to look:**
- `src/localization_bringup/config/`
- launch files in `src/localization_bringup/`

---

### 9) `navigation_bringup` (`navigation`)
**Purpose:** navigation bringup (Nav2 stack).

**How to run:**
```bash
docker compose -f docker/docker-compose.yml --profile navigation up --build
```

**What to watch when editing navigation params:**
- Costmap sources and topics
- Controller settings, planner settings, behavior tree XML
- Use_sim_time and clock setup (must be consistent)
- Namespacing: if you set `NAMESPACE`, the whole nav stack must follow it

**Where to look:**
- `src/navigation_bringup/config/`
- launch files in `src/navigation_bringup/`

---

### 10) `polaris_bringup` (`polaris`)
**Purpose:** planning stack / planning + navigation package.

**How to run:**
```bash
docker compose -f docker/docker-compose.yml --profile polaris up --build
```

**What to watch:**
- Polaris may depend on Nav2 topics / frames / behavior tree settings.
- Ensure it uses the same `map/odom/base` frames as the rest of your stack.
- If Polaris expects a specific global planner/controller, align configs accordingly.

**Where to look:**
- `src/polaris_bringup/config/`
- upstream Polaris repo / docs under `src/polaris_bringup/src/...`

---

### 11) `adaptive_filter_bringup` (`adaptive_filter`)
**Purpose:** runs `adaptive_odom_filter` to filter/fuse odometry streams.

**How to run:**
```bash
docker compose -f docker/docker-compose.yml --profile adaptive_filter up --build
```

**Typical config selection:**
- Environment variable: `PARAMS_FILE` or `CONFIG_FILE` set by compose.

**What to watch when editing adaptive filter params:**
- **Input topics** must exist and match:
  - `/odom`
  - `/imu/data`
  - `/ekf_loam/laser_odom_to_init` (or your SLAM odom topic)
- Output topic names: ensure downstream consumers subscribe to the correct output.
- Noise parameters: overly aggressive filtering can cause lag; too weak can cause jitter.

**Where to look:**
- `src/adaptive_filter_bringup/config/` (if you keep a copy there)
- upstream params in the adaptive filter package config

## Scripts

### `scripts/create_stack.sh`
Creates a profile list using `whiptail` and writes it to:

- `config/selected_profiles.conf`

This file is space-separated, e.g.:

```
ros_base scout realsense2 livox polaris fastlio2 pointcloud_to_laserscan adaptive_filter
```

### `scripts/run_robot.sh`
Reads `config/selected_profiles.conf`, builds the base image if needed, and runs:

- `docker compose -f docker/docker-compose.yml ... up --build`

> If `run_robot.sh` fails due to missing paths, ensure it resolves paths relative to the repo root (not your shell working directory).

## Debugging and Troubleshooting

### Check running containers
```bash
docker ps
```

### View logs
```bash
docker compose -f docker/docker-compose.yml --profile livox logs -f
docker compose -f docker/docker-compose.yml --profile fastlio2 logs -f
```

### Enter a container
```bash
docker exec -it <container_name_or_id> bash
```

### “env file not found”
- Make sure `config/.env` exists:
```bash
cp config/template.env config/.env
```

### “unable to prepare context: path not found”
- Your compose `build.context` path doesn’t match your folder name.
- Verify the directory exists and fix `docker/docker-compose.yml`.

### ROS setup scripts failing with `unbound variable`
- Do **not** use `set -u` in entrypoints that source `/opt/ros/jazzy/setup.bash`.

### Orphan containers warning
This is harmless; to clean:
```bash
docker compose -f docker/docker-compose.yml --remove-orphans up
```

## Support

If something fails:
1) Identify which profile/container is failing.
2) Check its logs.
3) Verify topic names + TF frames.
4) Verify parameter file path and that it is actually being loaded.

This stack is tailored for CORO/Petrobras OP-1319 robotics workflows and may require adjustments for different robots and sensors.
